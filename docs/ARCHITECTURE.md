# สถาปัตยกรรม

## สิ่งที่เลือกใช้

| ส่วน | ตัวเลือก | เหตุผล |
| --- | --- | --- |
| แอป | Next.js (App Router) + React + TypeScript | เว็บและ API อยู่ในโปรเจกต์เดียว รันและทดสอบบนเครื่องนี้ได้ทันที |
| มือถือ | เว็บแบบ mobile-first และ PWA | Android และ iOS เปิดจากเบราว์เซอร์หรือเพิ่มไปที่หน้าจอหลักได้ โดยไม่ต้องมีบัญชีร้านแอปในการส่งมอบรอบนี้ |
| ฐานข้อมูล | PostgreSQL 16 | ข้อมูลเด็กมีความสัมพันธ์และข้อจำกัดที่ต้องบังคับในฐานข้อมูล ไม่ใช่แค่ในหน้าจอ |
| โครงสร้างข้อมูล | Prisma Migrate | สคีมาและการเปลี่ยนโครงสร้างอยู่ในเวอร์ชันเดียวกับโค้ด |
| ตรวจข้อมูลนำเข้า | Zod | ปฏิเสธเบอร์โทร วันที่ จำนวนเงิน และเนื้อความที่ผิดรูปแบบก่อนถึงฐานข้อมูล |
| การเข้าสู่ระบบ | คุกกี้ httpOnly ที่เพิกถอนในตาราง Session ได้ | ธุรกิจนี้ไม่ต้องพึ่งผู้ให้บริการล็อกอินรายอื่น และทดสอบสิทธิ์ได้ตรง ๆ |
| ทดสอบ | Vitest กับฐานข้อมูลทดสอบ | ทดสอบล็อกอิน สิทธิ์ การรับส่ง การแจ้งหยุด คีย์ซ้ำ และคิวซิงก์กับข้อมูลจริง |
| ค่าโดยสาร | บันทึกเงินสดหรือการโอนโดยเจ้าของ | ยังไม่เชื่อมเกตเวย์ชำระเงิน เพราะธุรกิจนี้รับเงินเอง |
| การแจ้งเตือน | รายการในฐานข้อมูลของระบบ | ยังไม่ส่งข้อมูลเด็กไปยังผู้ให้บริการพุชจนกว่าจะมีคีย์และข้อตกลงเรื่องผู้ประมวลผลข้อมูล |

ไม่ได้เลือกแอปเนทีฟแยกคนขับและผู้ปกครอง เพราะเจ้าของคนเดียวต้องดูแลทั้งสามบทบาท ชุดโค้ดเดียวที่รันได้จริงสำคัญกว่าการมีแพ็กเกจร้านแอปที่ยังตรวจบนเครื่องนี้ไม่ได้

## โครงสร้างโฟลเดอร์

```text
docs/                 ความต้องการ สถาปัตยกรรม ข้อสมมติ ความปลอดภัย พจนานุกรมข้อมูล
prisma/               schema, migrations, seed สำหรับพัฒนาเท่านั้น
src/app/              หน้าจอและ route handlers
src/components/       ส่วนหน้าจอที่ใช้ร่วมกัน
src/lib/              ฟังก์ชันบริสุทธิ์ที่ทั้งหน้าจอและเซิร์ฟเวอร์ใช้ได้
src/server/           กติกาธุรกิจ ธุรกรรม สิทธิ์ และการเขียนประวัติ
tests/                เทสอัตโนมัติ
scripts/              สร้างเจ้าของคนแรกบนระบบจริง
public/               ไอคอนและ service worker ของเชลล์แอป
```

หน้าจออ่านข้อมูลผ่านเซอร์วิสโดยตรง ส่วนที่กดบันทึกเรียก API เส้นทางเดียวกับที่คิวออฟไลน์ใช้ จึงไม่มีปุ่มที่เขียนคนละกติกากับเซิร์ฟเวอร์

## เส้นทางข้อมูล

1. ผู้ใช้ส่งคำขอพร้อมคุกกี้เซสชัน
2. Route handler ตรวจที่มาของคำขอ รูปแบบข้อมูล และบทบาท
3. เซอร์วิสเปิดธุรกรรม เขียนสถานะ เหตุการณ์ การแจ้งในแอป และ audit ในชุดเดียวกัน
4. ตอบ `confirmed: true` หลังธุรกรรมสำเร็จเท่านั้น
5. ถ้าเบราว์เซอร์ส่งคำขอไม่ถึงเซิร์ฟเวอร์ คิวในเครื่องเก็บคีย์เดิมไว้ และหน้าจอแสดงว่ารอซิงก์

คีย์ idempotency อยู่ที่เหตุการณ์รับส่ง คำขอหยุด การชำระเงิน และกล่องซิงก์ การกดซ้ำด้วยคีย์เดิมได้ผลเดิม การกดคนละคีย์แต่เปลี่ยนสถานะซ้ำถูกดัชนีฐานข้อมูลปฏิเสธ

## เขตเวลา

วันให้บริการคำนวณตามปฏิทินเอเชีย/กรุงเทพ เวลาที่ถือว่าบันทึกแล้วคือเวลาเซิร์ฟเวอร์ เวลาที่เครื่องผู้ใช้กดเก็บเป็นข้อมูลประกอบ ไม่ใช้แทนเวลาบันทึก

## สิ่งที่ service worker ทำและไม่ทำ

ตัว service worker เก็บเชลล์ของหน้าที่เคยเปิด และไม่ยุ่งกับคำขอ POST ไปที่ API จึงไม่สามารถตอบสำเร็จแทนเซิร์ฟเวอร์ได้
